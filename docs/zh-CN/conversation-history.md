# 以前的对话

[English](../conversation-history.md) | 简体中文

经过网关的每一轮对话都会记进一个本地库，agent 之后可以翻出别的平台、别的话题、别的
agent 里说过的事，隔几天几周都行。这是网关自己的记录，不是 harness 的：你在终端里直接
开的 Claude Code 或 OpenCode 会话不在里面。

库文件是 `<配置目录>/history.db`，网关首次启动时创建。权限 `0600`，和
`conversations.json` 放在一起，内容敏感程度与各 harness 自己的会话文件相同。

## 记什么

按所属会话逐条记：

- 一轮发给 agent 的那段话——附件只记文件名，不记内容；
- agent 的完整回复；
- 每个工具调用一行：先是它那一行（`Bash: git status`、`Read: src/daemon/turn-runner.ts`），下面是
  完整参数——heredoc、编辑的替换内容、写入文件的内容（最多 10 万字符，更长的会注明截掉了多少）。
  工具的输出不记：它比参数大好几倍，agent 从中得出的结论在它的回复里。

参数是流式下发的 harness，一个调用会在参数到达过程中发好几次；库里只为它留一行并原地改写，
最终是这个调用实际运行时的参数。在此之前（2026-11-06）写下的行，同一个调用可能有好几行，
而且只有那一行、没有参数。

普通对话之外的事情也记，并标上类型：定时任务的一次运行（`schedule`）、子代理的话题或
`[sub-agent updates]` 汇报卡片（`subagent`）、agent 在轮次结束后才报回来的输出
（`background`）。会话的类型取它第一轮的类型；之后某一轮的类型记在那一轮自己的行上。

**写入失败绝不影响这一轮。** 磁盘满了、库打不开，网关记一条日志照常回答；回答才是要紧的，
索引不是。

## 轮次

网关在一轮运行期间写下的每一条记录都属于那一轮。一轮是网关交给 agent 的一件事：开头的那段话（或中途并入的那条消息）、
它做的工具调用、结尾的回复。每一轮另有一行自己的记录：

- 回答它的 agent，以及这个会话的**代次**——`/new` 和 `/cd` 销毁 agent 会话时会加一，
  重置前后的轮次因此能分开；
- 开始时间和结束时间；
- 触发来源：人发的消息（`person`）、定时任务（`schedule`）、失败后的自动继续（`continue`）、
  交给子代理的任务（`delegate`）、`[sub-agent updates]` 卡片（`update`）、
  agent 在轮次结束后报回的输出（`background`）；
- 结局：`done`、被停（`stopped`）、失败（`failed`），以及 `restart`——网关没跑完的那一轮，
  下次启动时从仍然标着「进行中」的行认出来。这种轮的结束时间只是下界：它写下的最后一条消息
  的时间。

归属规则：

- 一轮运行期间插话、被并入的消息属于**这一轮**；
- harness 收下了、但在它自己另起的一轮里回答的消息（`detached`）不归入任何一轮：它的回答会以后台输出
  的形式回来，而把提问算进刚结束的那一轮，会让那一轮看起来回答过一个它没答的问题；
- 回复封口之后 agent 才报回来的输出自成一轮（`background`）：算进原来那一轮，就会把话记在
  那一轮结束之后。被 `/stop`、被新的一轮接管、或 agent 进程退出打断的后台输出记为 `stopped`；
- 定时任务自成一**轮**（`schedule`），即使它是说进一个普通话题里的；
- 被停的轮保留已经写下的内容。它确实跑过，半截回复也是真的。

已有的 `history.db` 原地迁移：加上 `turn` 和 `call` 列，旧行留空，读出来是轮次 `?`、结局 `unknown`。
不会给旧行补造轮次。从 web UI 转录导入的行同样没有轮次——写下它们的是 web UI，不是某一轮。

## 读其中一部分

```bash
talkcode sessions read '#12' --turn last
talkcode sessions read '#12' --turn done
talkcode sessions read '#12' --turns 3
talkcode sessions read '#12' --turn 2 --role agent
talkcode sessions read '#12' --since '#87'
talkcode sessions read '#12' --grep 超时
talkcode sessions read '#12' --role tool --tail 20
```

- `--role user|agent|tool`：只看这个角色的行。
- `--turn last|done|<n>`：最近一轮、**当前 agent 和代次**里最近一个正常结束的轮、这个会话里的第 `n` 轮
  （从 1 数）。`--turns <n>` 取最近 `n` 轮（最多 100 轮，截断时 note 会说明）。刚 `/new` 完、新代次
  还没有结束的轮时，`--turn done` 返回空，并在 note 里说明。
- `--since <消息>`：这条消息 id 之后（不含）的行，id 来自上一次读。按写入顺序（id，也就是续读用的
  那个坐标）返回，所以后来导入的转录可能不按时间排列。碰到上限时，note 会给出下一次 `--since`
  该用的 id。它不能和 `--turn`、`--turns`、`--tail` 一起用：那些从最新一端读，一个游标没法同时
  服务两个方向。
- `--grep <文字>`：只在这个会话里找包含这段文字的行。
- `--tail <n>`：配合 `--role tool`，取最近 `n` 行工具调用。

这些筛选可以叠加（AND），但 `--since` 与轮次筛选或 `--tail` 的组合会被拒绝，而不是猜一个语义。
带筛选的读会额外打印每行的轮次、那一轮的结局和 agent。`--around`
不能和它们一起用：它自己定义了一段窗口。

**工具调用会折叠。** 没有用 `--role` 或 `--grep` 挑行的读，会把每一串连续的工具调用合成一行，
单个调用只留它的第一行：

```text
[37 tool calls: Bash ×20, Edit ×12, Write ×5]
```

一个干活的会话里大部分是工具调用——11 月两天里记下的行有 94% 是它——不折叠时读出来是一页命令，
人说的话夹在中间。一串不会跨两轮。`--role tool` 连参数逐条列出，`--grep` 命中的调用整行显示，
`--around` 的窗口不折叠；折叠过时 note 会说明。

每次读都有上限：500 行（折叠后的一行算一行）、20 万字符。碰到上限会说明漏掉了多少行、从哪一端截的——尾部读
（`--turn`、`--turns`、`--tail`）保留最新的行，普通读和 `--since` 读保留最早的行。

## 怎么查

```bash
talkcode sessions search 跨会话查询
talkcode sessions search 部署 --agent cc --days 30 --limit 20
talkcode sessions search 'git push' --tools
talkcode sessions read '#12' --around '#87' --window 10
talkcode sessions list --days 7
```

`search` 返回会话 id、消息 id、日期、标题、agent、平台和命中的片段。它搜的是人和 agent 说的话；
加 `--tools` 连工具调用（含参数）一起搜。`read` 接会话 id，
从最早一条往后打印；`--around <消息>` 以某条为中心，前后各显示 `--window` 条（默认 10）。
`list` 是最近活跃的会话。

检索是关键词检索（BM25），不做向量。中文能搜到靠两点：

- **连续汉字在入库时切成两两重叠的二字词**——「跨会话查询」变成
  `跨会 会话 话查 查询`。SQLite 默认分词把整段汉字当一个词，搜不到里面的「查询」；
  它的 `trigram` 模式又搜不到两个字的词。切分在 JS 里做，入库和查询走同一套，所以
  两个字的搜索词本身就是索引里的一个词。
- **单个字退回子串匹配**，因为一个字太常见，全文命中说明不了什么。

定时任务的输出排在普通对话后面，再按相关度、时间倒序——否则一个每分钟跑一次的任务会把
用户真正要找的对话挤下去。

## 补历史

网页端从 2.13.0 起就把每个话题的记录存在磁盘上（[网页端](web-ui.md#要有的预期)）。
第一次带着库启动时，这些记录连同话题标题一起导入，历史不会从空白开始。每个文件只导入一次，
重启不会重复。Telegram、Discord、Slack 等平台上的旧对话没法从平台读回来，那些对话从开启
这个功能的那天开始记。

## 隐私

库里有每一段提问和回复的全文，包括 agent 读过的内容。敏感程度和各 harness 自己的会话文件
一样，所以权限是 `0600`，并且和配置放在同一目录。删掉 `history.db` 就删掉了整个库；网页端
的记录不受影响，之后再启动会重新导入（“只导一次”的记号也随文件一起没了）。
